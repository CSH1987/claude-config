# 기획(Planning) 플레이북 — 정식 채택 검토 제안

## 배경

`claude/playbooks/`에는 요구사항 확정(requirements)·리서치(research)·의사결정(decision)·검토(review) 4종이 있지만, "여러 작업/결정이 얽혀 있고 순서를 잘못 정하면 재작업 비용이 큰" 상황(예: 다팀 마이그레이션, 다중 의존관계가 있는 기능 빌드) 자체를 다루는 플레이북은 없었다. 이 공백을 메우기 위해 5인 전문가 패널 토론(`expert-debate`)으로 초안 뼈대를 잡고, GitHub 인기 저장소(rust-lang/rfcs, thecodedrift/rfc, KhazP/vibe-coding-prompt-template 등)의 구조적 패턴과 내부 OMC 시스템(`deep-interview`, `planner` 등)의 게이팅 원칙을 마이닝했다. 여기에 메타 프롬프트 설계 기법(서술형 대신 이진 게이트, 자기검증 루프 내장, 안티패턴 명시)과 실무 프레임워크(Amazon PR/FAQ, RFC 프로세스, Design Doc, Shape Up, SPADE)의 핵심 아이디어를 접목해 초안 v1을 만들었다. 이후 서로 다른 세 시나리오(다팀 풀코스 / 순서 명확한 중간규모 / 1인 다중부모 최소골격)에 실제로 적용 → 완결성·실행가능성 관점 비평 → 개선을 3회 반복해 v4로 수렴시켰다. 이 문서는 그 v4를 정식 채택(플레이북 승급) 검토용으로 정리한 것이다.

```markdown

# Playbook — 기획 (Planning)

> 핵심 한 줄: **여러 조각이 얽히면, 순서를 기억이 아니라 문서로 고정한다.** 순서를 즉흥으로 정하면 재작업으로 돈다.

## 언제 쓰나
- Gate A(진입, 하나라도 해당): (a) 2개 이상 작업/결정이 시간순·의존관계로 얽혀 있다 OR (b) 단일 항목이라도 원상복구 소요(시간/돈/평판)가 크다 — 예: 마이그레이션 롤백 / 집행 광고비 / 계약 위약금(동등 병렬, 도메인 무관 — 예시일 뿐 소진적 아님).
- 둘 다 아니면 이 문서 없이 바로 실행(오버헤드 회피).
- 얽힘 없이 비가역 결정 하나뿐이면 → 이 문서를 거치지 말고 바로 [decision.md](./decision.md).

## 방법
1. **무게 판정(Gate B)** — 진입 후 2기준 중 하나라도 예 → 풀코스, 둘 다 아니오 → 최소골격: (1) 확산 범위 — 타 팀/세션(1인 단독 운영이면 "미래 세션의 나 자신")이 이 산출물을 전제로 이미 일정을 짰거나 짤 가능성을 **구체적으로 지목 가능한가**(추측이면 아니오) (2) 재작업 규모 — 순서 오류 시 재작업 범위가 **크다고** 구체적으로 지목 가능한가(막연하거나 작으면 아니오 — 작은 재작업까지 "예"로 잡으면 항상 풀코스로 밀림). 둘 중 하나라도 "모름"이면 requirements.md 선행 후 재판정. (구 기준 "다중부모 의존 예상"은 착수 전 사전판정이 구조적으로 낙관적 "아니오"를 유도해 제거 — 4번에서 실행배열 초안 후 재확인한다.)
2. **타임박스 선언(2종)** — ① 문서화 자체 상한(최소골격 15분, 풀코스는 자체 선언) ② 실행 페이즈 상한, 없으면 "태스크별 완료조건이 상한선"임을 명시. 자체 선언 시 근거 1줄 필수(6번 레퍼런스 클래스 인용, 없으면 "레퍼런스 없음 — 보수적으로 X"; 6번이 아직 미작성이면 "미정(6번 작성 후 소급)"으로 임시 기입하고 순서대로 진행). 초과 시: 비가역 결정 없이 축소 가능하면 범위축소, 아니면 중단 — 침묵 초과 금지.
3. **범위 IN/OUT** — 한 줄씩. 변경은 decision.md 경유 명시적 재결정으로만.
4. **실행 배열(선행조건표, DAG)** — 열: id·완료조건·depends_on·priority·owner, 템플릿 유무와 무관하게 이 열 그대로 즉시 사용(정식 스키마는 `claude/templates/plan-record.md`, promote 시 신설·있으면 우선). priority 기본 P0/P1/P2, 안 맞으면 문서 상단에서 1회 재정의. owner 열은 항상 유지하고(칸 삭제 금지) 1인 운영자는 값에 "나"를 채우며, 미정이면 "TBD(확정기한)" 명시 — 미정이 표 착수를 막지 않는다. 완료조건엔 "어떻게"를 섞지 않는다 — 판별: "~인가?"로 바꿔 참/거짓 검증되거나 이해관계자 명시 승인으로 판정되면 완료조건, 수단·절차면 구현법(칸 밖). 착수가능목록(ready set)을 문서 상단에 노출. 최소골격은 순서 목록+완료조건 인라인으로 완화하되, **초안 작성 후 다중부모(태스크 하나가 선행 2개+)가 드러나면 즉시 표로 승격하고 Gate B의 2기준을 재평가한다**(강제 격상이 아니라 재평가 의무화 — 결과가 최소골격으로 남을 수도 있으며, 그 경우 근거를 5번 가정 로그에 1줄 기록; 표 승격이 일어나면 2번 문서화 타임박스도 자동 재선언 대상이다 — 근거 1줄 추가, 기존 상한 자동승계 아님).
5. **가정·리스크 로그 & 비가역 결정 위임** — 가정 로그는 무게 무관 필수(최소골격은 1문장 압축, "가정 없음"도 유효). 열: 가정｜근거｜검증여부｜붕괴시영향｜조기신호(4번과 같은 표 규칙). 비가역 결정 판별: 조직 경계를 넘어 계약/예산/정책/대외관계에 묶이는가 → 예=decision.md로 위임(이 문서엔 `(→ decisions/<machineId>/<YYYYMMDD-slug>.md)` 링크만) / 아니오(실행 순서·타이밍 리스크)=이 가정 로그(붕괴시영향) 또는 4번 완료조건(안전장치)에 남긴다.
6. **프리모템 & 레퍼런스 클래스** — "이미 실패했다"고 가정하고 구체적 실패 시나리오(S1, S2…)를 review 재호출 없이 이 문서 자체 스텝으로 남긴다. 레퍼런스 클래스("비슷한 과거 작업이 실제로 어땠나", 가정·프리모템 ID 괄호 병기 가능)는 가중치 무관 필수(최소골격도 1줄, "레퍼런스 없음(신규 유형)"도 유효). 기본은 계획 전체 1줄, 태스크별로 유사경험 여부가 상이하면 4번 표에 열 추가 가능.
7. **재검토/킬 트리거 & 실행 중 갱신** — 발동 조건과 조치를 사전 확정(발동 시 재량 판단 금지). 실행 중 갱신은 append-only(삭제 금지, 취소선만); 가정 ID(A1…)는 완료조건 각주로, 프리모템 ID(S1…)는 완료 선언 시(각 태스크 완료 시점마다 수행, 계획 전체 완료 시 종합 1회 추가) 3분류(추정오류｜실행오류｜외부변화)로 상호 참조 — 새 필드를 늘리지 않는다.

## 품질 바
- Gate A/B 판정과 근거가 한 줄로 적혀 있다(Gate B는 확산범위·재작업규모 각각 "구체적으로 지목 가능"으로 판정, 모름이면 requirements.md 선행).
- 실행 배열의 모든 항목에 완료조건이 있고(구현법과 안 섞임, "~인가?"로 판별 가능하거나 이해관계자 명시 승인형 — 나쁜예: "사용자가 만족한다" / 좋은예: SW="2클릭 내 X 완료", 비SW="주간 대리지표 Y가 임계 Z 도달"), 착수가능목록(ready set)이 드러난다.
- 가정·리스크 로그가 존재하고(비어도 "없음" 명시), owner 열이 유지되며 미정은 "TBD(확정기한)"로 명시돼 있다(빈칸·칸삭제 금지).
- 재검토/킬 트리거에 발동 조건과 조치가 둘 다 있고, 비가역 결정은 decision.md로 위임돼 이 문서엔 링크만 있다.
- 타임박스가 문서화·실행 페이즈 각각(또는 생략 사유) 선언돼 있고 초과 시 판단 근거가 있으며, 표 승격/격상 시 문서화 타임박스가 재선언돼 있다.
- 프리모템 시나리오(S1…) 최소 1개, 레퍼런스 클래스 1줄이 있다(가중치 무관 필수, "없음"도 유효).
- 실행 중 갱신이 append-only이고 A/S ID가 완료조건·3분류로 상호 참조되며, 최소골격에서 도중 격상됐다면 격상 시점·사유가 1줄 병기되고, 완료(또는 첫 킬 트리거 발동) 시점에 "골격 판정이 맞았는가"를 사후검증한다.

## 흔한 실패
- 계획 도중 비가역 결정까지 그 자리에서 내림(위임 안 함) → 나중에 근거 추적 불가.
- DAG 없이 산문으로만 순서 서술 → ready set 파악 불가, 의존관계 유실.
- 다중부모 의존을 착수 전에 낙관적으로 "아니오"로 넘기고 4번 재확인을 생략 → 뒤늦게 이중의존 발견.
- 가정 로그 생략 → 붕괴 신호를 사후에야 알아챔.
- 프리모템 생략 또는 review 단계로 미룸 → 낙관 편향이 실행 내내 유지.
- 타임박스 없이 착수 → 무한 확장(스코프 크리프).

## 이 시스템과 연결
- 모호함이 남아 있으면(Gate B "모름" 포함) 먼저 [requirements.md](./requirements.md)로 닫는다.
- 개별 비가역 결정은 [decision.md](./decision.md)로 `decisions/<machineId>/<YYYYMMDD-slug>.md`에 기록(판별 규칙은 5번).
- 이 계획 문서 자체는 `decisions/<machineId>/<YYYYMMDD-slug>-plan.md`로 저장(decision.md와 폴더 공존, 파일명 접미사로 구분 — 교차세션 발견성 유지).
- 완료 선언 직전엔 [review.md](./review.md)(적대적 검증) — 프리모템 3분류(7번)는 review.md 재호출 없이 이 문서 자체에서 완결.
- 큰/복잡 스펙 → `/deep-interview`(모호도 게이팅). 실행 위임(`/ralph`·`/team`·`/autopilot`)은 사용자의 별도 명시적 선택 필요 — 이 문서는 그 전까지 pending approval 상태로 멈춘다.
- 고위험 신호(원칙: 대외 공표·계약·법적 노출·되돌리기 어려운 손실을 수반하는 변경) 시 자동으로 풀코스+확장 검증으로 격상 — 예: 보안/인증·데이터 마이그레이션·프로덕션 인시던트 / 법무·컴플라이언스 위반·계약 파기·브랜드 위기(도메인별 예시, 동등 병렬).
```

## 3회 반복 개선 이력

**라운드 1 — 신규 협업 툴 도입(다팀, 마이그레이션+교육+일정조율이 얽힘, 되돌리기 비용 큼).** Gate B 풀코스로 진입해 실행배열·가정로그·프리모템·킬 트리거까지 전 구간을 실제로 채워봤다. 비평에서 5가지 완결성 문제(미확정 이견이 본문에 노출됨, 표 스키마가 방법 단계에 그대로 박혀 분량이 siblings 대비 60%+ 김, 계획 문서 자체의 저장 위치 미확정으로 테스트 결과에 파일 경로가 아예 안 나타남, owner 다중값 표기법 미규정, 품질 바가 11단계 중 절반만 커버)와 4가지 실행가능성 문제(타임박스 적용 대상 모호, 세 그릇 중 어디에 담을지 판별 규칙 불명 등)가 드러났다. 이번 라운드에서 저장 경로(`-plan.md` 접미사)와 다중부모 발견 시 즉시 표 승격 규칙을 확정했고, Gate B 두 기준에 "구체적으로 지목 가능한가" 앵커를 추가해 순수 이분법을 줄였다. 표 2개(실행배열·가정로그)는 인라인 markdown table을 걷어내고 템플릿 참조로 전환해 분량을 siblings 수준으로 되돌렸다.

**라운드 2 — 분기 콘텐츠/마케팅 캠페인(제작→검수→배포 순서는 명확하지만 확산 범위는 작음).** Gate B 최소골격으로 진입했으나, 실행배열을 산문으로 쓰다가 배포 태스크가 검수·슬롯확보 둘 다에 의존하는 이중의존(다중부모)이 뒤늦게 드러나 표로 즉시 승격했다. 비평에서 방법이 11단계·품질바 10개로 다른 플레이북(4~6단계, 3~5개)보다 여전히 무겁다는 점, `plan-record.md` 템플릿이 미존재라 표를 프리핸드로 고안해야 했던 점, Gate B가 "모름" 상태를 다루지 않아 상위 원칙(requirements.md 선행)과 충돌한 점, 그리고 다중부모 사전판정이 "표를 그려야만 드러난다"는 구조적 모순으로 항상 낙관 오답을 유도한다는 점이 지적됐다. 이에 따라 다중부모 사전판정을 아예 제거해 표 작성 후 재확인으로 순서를 뒤집었고, "모름"이면 requirements.md 선행을 명문화했으며, 방법을 11→7단계로 압축하고 표 열을 방법 4번에 인라인 명시해 템플릿 부재와 무관하게 즉시 쓸 수 있게 했다.

**라운드 3 — 개인 사이드 프로젝트(다중부모 관계가 이미 설계상 존재: B·C가 A에 의존, D가 B·C 둘 다에 의존, 대외 확산 없음).** 착수 전 최소골격으로 판정했다가 실행배열 표 작성 중 D의 이중의존이 드러나 즉시 표 승격+Gate B 재평가가 실제로 작동함을 확인했다(1인 프로젝트에서도 동일 패턴 재현). 비평에서 분량이 여전히 siblings보다 1.6배 길고 유일하게 본문 밖 트레일링 주석 부록을 가진 점, Gate B 확산범위 판정문이 "타 팀 존재"를 전제해 1인 시나리오엔 판정 대상이 모호한 점, owner 열의 output·size 필드가 정의되지 않아 실제로 못 쓰인 점, 레퍼런스 클래스·완료 선언이 다중 태스크 DAG에서 어느 단위(계획 전체 vs 태스크별)를 가리키는지 불명확한 점이 지적됐다. "1인=미래 세션의 나" 대리기준을 추가하고, owner는 "칸 유지+값은 '나'"로 확정, output·size는 미사용이라 삭제, 완료 선언을 "태스크별+계획 전체 종합" 2레벨로 명시했다. 이 라운드에서 "Gate B 재판정"이라는 표현을 "재평가"로 최종 확정했다(강제 격상이 아니라 재평가 의무화이며 결과가 최소골격으로 남을 수도 있음을 명확히 함). 품질 바도 10→7개로 재압축했다.
