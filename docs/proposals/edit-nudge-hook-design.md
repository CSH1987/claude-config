# 대형 코드 작업 도구 라우팅 넛지 — 아키텍처 결정 (US-001)

## 배경
2026-07-13~14 세션 감사에서, 89~132회 액션(Bash/Edit/Write)짜리 대형 코드 작업(근본원인 디버깅·신규 기능 빌드)일수록 Skill/Agent/MCP 확장도구 사용률이 오히려 0%로 떨어지는 역설을 발견. CLAUDE.md에 "규모가 클수록 code-review/전문 에이전트 경유" 프롬프트 지침을 추가했으나, 이 자체도 프롬프트 지침이라 큰 작업 도중 컨텍스트에 묻혀 잊힐 위험이 원래 문제와 동일하게 남음. → 프롬프트가 아닌 **결정적(deterministic) 훅**으로 강제 필요.

## 원래 목표 (제약조건)
1. 최근 Skill/Agent/Task/mcp__* 호출 이후 Edit/Write가 임계치(6회) 이상 누적되면 넛지
2. 하드 블록 아닌 리마인더(작업 흐름 방해 금지)
3. **스팸 금지** — 매 Edit마다 반복 발화 금지, 임계치 도달 시 1회(또는 리셋 전까지)만
4. 순수 조사(Read/Grep/Bash)는 카운트 제외, 실제 코드 변경(Edit/Write)만 카운트
5. 세션별 상태 격리(이전 세션 카운트가 새 세션에 유입되면 안 됨)

## 옵션 비교

| | A. hookify `stop` 이벤트(전체발화) | B. 커스텀 상태훅(PostToolUse) | C. hookify `file` 이벤트(경로매칭) |
|---|---|---|---|
| 구현 난이도 | 매우 낮음(`.local.md` 1개) | 중간(훅 스크립트+state 파일 I/O) | 매우 낮음(`.local.md` 1개) |
| 카운팅/상태 | ❌ 불가능(hookify 규칙엔 세션 간 상태 없음) | ✅ 실제 카운터 | ❌ 불가능 |
| 제약1(임계치 기반) | ❌ 미충족 — 항상 발화 | ✅ 충족 | ❌ 미충족 — 매 파일마다 발화 |
| 제약3(스팸 금지) | ❌ **위반** — 사소한 턴에도 매번 발화 | ✅ 충족(already-fired 가드) | ❌ **위반** — 가장 흔한 이벤트라 더 심함 |
| 제약4(코드만 카운트) | N/A | ✅ 충족(tool_name 필터) | 부분 충족(경로 필터는 되나 카운팅 자체가 없음) |
| 제약5(세션 격리) | 해당없음(카운트가 없으므로) | ✅ session_id 키로 파일 분리 | 해당없음 |

**A/C는 hookify 규칙 형식 자체의 한계(세션간 상태 없음)로 핵심 제약(3)을 구조적으로 위반한다 — 패턴/임계치를 아무리 다듬어도 고칠 수 없는 근본적 한계.**

## 결정: **옵션 B — 커스텀 상태훅**

### 아키텍처
- **훅 이벤트**: `PostToolUse` 단 하나만 사용(SessionStart 불필요 — session_id로 상태파일을 키잉하면 새 세션은 파일이 아예 없어 count=0부터 자연히 시작함).
- **상태 파일**: `~/.claude/hookify-state/edit-nudge-{session_id}.json` — `{"count": 0, "fired": false}`
- **로직**(PostToolUse 훅, stdin JSON의 tool_name 검사):
  - `tool_name`이 `Edit`|`Write` → count += 1
  - `tool_name`이 `Skill` 또는 `Agent`|`Task` 또는 `mcp__*` 접두 → count = 0, fired = false (리셋)
  - count ≥ 6 AND fired == false → PostToolUse 훅 출력 프로토콜(`hookSpecificOutput.additionalContext`)로 넛지 메시지 주입, fired = true 로 기록
  - 그 외(Read/Grep/Bash 등) → 카운트 변화 없음, 그냥 통과
- **격리**: session_id가 파일명에 들어가므로 이전 세션 상태가 새 세션에 안 섞임.
- **정리**: 오래된 상태파일(예: 7일 이상)은 훅 실행 시 opportunistic하게 정리(선택사항, 기능 요구사항 아님).

### 트레이드오프
- A/C 대비 구현·유지보수 비용이 더 든다(스크립트+상태파일 관리) — 하지만 이게 유일하게 원래 제약을 전부 충족하는 옵션이라 감수할 가치가 있음.
- 병렬 도구 호출(한 턴에 여러 도구 동시 호출) 시 파일 쓰기 경합 가능성 — 이 유스케이스는 카운트가 정확히 6이어야 하는 게 아니라 "대략 그 언저리에서 한 번 알림"이면 충분해 엄격한 락 불필요, 단순 read-modify-write로 충분.
