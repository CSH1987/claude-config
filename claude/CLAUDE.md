# 전역 세션 기본값 (모든 프로젝트 · 모든 머신)

이 파일은 claude-config 레포로 관리되며 `~/.claude/CLAUDE.md` 로 배포되어 모든 프로젝트의 모든 세션에 자동 로드됩니다.

## 응답 언어 (최우선)

- **항상 한국어로 답하세요.** 사용자가 영어로 묻거나 입력이 영어여도 기본 응답 언어는 한국어입니다.
- 예외: 코드·명령어·로그·식별자·고유명사·인용문 등 원문 그대로여야 하는 부분은 번역하지 않습니다. 설명·요약·제안은 한국어로.
- 사용자가 특정 답변에서 명시적으로 다른 언어를 요청하면 그때만 그 언어로 답합니다.

## 명명 규칙 (직관적 이름 · 최우선)

- **모든 이름·명칭은 직관적으로.** 레포·디렉터리·파일·변수·함수·식별자·프로젝트명 등 무엇이든 *그것이 무엇인지 한눈에 드러나는* 명확하고 일반적인 이름을 씁니다. 축약·내부 농담·모호한 코드명(예: `medtour-tracker` 같은 contraction)은 피하고 설명적이고 단순한 이름(예: `tracker`)을 우선합니다.
- 사용자가 특정 이름을 **명시적으로 지정하지 않는 한** 이 원칙을 기본으로 지킵니다. 이름을 새로 만들거나 제안할 때 직관성을 1순위 기준으로 삼고, 모호하면 더 명확한 쪽을 택하세요.

## 작업 강도 기본값 (최우선 · 적응형 이펙트 정책)

- effort는 **모델과 대칭되는 하이브리드 구조**입니다: 모델이 계획=최상위/실행=효율 모델로 나뉘듯(아래 "모델 전략" 참조), effort도 **판단력이 결과를 좌우하는 작업=xhigh, 절차 수행형 실행 작업=high(바닥값)** 로 다룹니다.
- **영구 적용되는 부분(바닥값)**: `effortLevel: "high"` 가 `~/.claude/settings.json` 에 설정돼 있어 매 세션 자동으로 최소 high 추론입니다.
- **자동 전환이 불가능한 이유(사실 확인됨)**: 모델의 `opusplan`은 Claude Code 엔진이 plan 모드 진입/이탈을 내부적으로 감지해 자동 전환하지만, `effortLevel`엔 그런 phase-aware 메커니즘이 없습니다 — 세션 전체에 적용되는 단일 정적값이며, 훅으로도 흉내낼 수 없습니다(엔진 내부 모드 변화는 훅이 감지 못 하고, 훅 프로세스의 env 변경은 부모 세션에 전파되지 않는 프로세스 격리 제약). 따라서 계획→xhigh, 실행→high 전환은 **자동이 아니라 제안 기반**입니다.
  - 기획·설계·아키텍처 판단·근본원인 디버깅·보안/비평 리뷰처럼 **판단력이 결과를 좌우하는 작업**을 시작하기 전에는 먼저 이렇게 제안하세요:
    > "이 작업은 판단력이 결과를 좌우해서 `/effort xhigh`로 올리는 걸 권장합니다. 실행하시겠어요?"
  - 동의하면 사용자가 직접 `/effort xhigh` 를 실행해야 합니다 (훅·Claude 는 슬래시 명령을 대신 실행할 수 없음). 절차 수행형 실행 작업은 바닥값 high 그대로 진행하면 됩니다.
- **자동 실행되는 부분**: `claude` 명령이 셸에서 `--settings ~/.claude/ultracode.json` 으로 오버라이드돼 있어, 새 세션은 보통 **ultracode 가 이미 켜진 상태**로 시작됩니다. 이 경우 시스템 리마인더에 `Ultracode is on` 이 표시됩니다 → **추가 조치 불필요**.
- **영구화가 불가능한 부분**: ultracode 의 *동적 워크플로 오케스트레이션* 과 ultraplan 은 Claude Code 설계상 세션 전용입니다 (settings.json·환경변수·훅으로 영구화 불가). 세션이 ultracode 가 아니라면 본격 작업(특히 복잡/다단계/대규모) 전에 `/effort ultracode` 를 제안하세요.
- 단순/사소한 작업은 굳이 제안하지 말고 그대로 진행하세요 (불필요한 오케스트레이션 비용 회피).

## 모델 전략 (적응형 플랜)

- 전 머신 공통 기본은 **적응형 플랜(adaptive plan)** 입니다: settings 의 `"model": "opusplan"`(Claude Code 내장 별칭 — 이 설정값 문자열 자체는 바꿀 수 없음) + env 별칭 재매핑으로 구현됩니다. 플랜 단계=최상위 모델(`ANTHROPIC_DEFAULT_OPUS_MODEL`), 실행 단계=효율 모델(`ANTHROPIC_DEFAULT_SONNET_MODEL`), 결정 지점 보강=`advisorModel: fable`.
- **최고 모델 직지정(예: `"model": "claude-fable-5[1m]"`)은 쓰지 않습니다.** 새 프런티어 모델이 나오면 model-watch 가 env 재매핑만 갱신하고 레포 settings 에도 반영해 config-sync 로 전 머신에 자동 전파합니다 (`model` 별칭은 그대로 유지 = 적응형).
- 명칭: 이 구성을 대화·문서에서 "opusplan"이 아니라 **"적응형 플랜"** 으로 부릅니다.
- 규모가 큰 작업(코딩·비코딩 공통)에서는 설계(top)→검토(mid, headless 전용 신설 env 슬롯)→최종산출(exec) **3단 릴레이**가 자동 적용됩니다(고위험만 반려 게이트, 미달 시 기존 단일 위임 유지). 라우팅 규약·측정 규약 상세는 `workload-optimization` 스킬의 "3단 릴레이" 절 참조.
- **3티어 워크포스 (2026-08-20)**: Fable=기획(top, 스스로 방향을 정하는 판단)·Opus 5=검증·리뷰·판정(mid, 주어진 기준으로 판정만 — code-reviewer/security-reviewer/verifier)·Sonnet=구현(exec). Workflow `agent()`에 mid를 구체 id로 명시하는 경로가 실제로 존재합니다(2026-08-20 실측 확인) — 상세 규약은 `workload-optimization` §5.10. 매주 학습파이프라인의 `lens:routing`이 지출·반려율·규약 위반을 실측해 라우팅 개선을 **드래프트로만** 제안하고(Vault `90_Hermes/라우팅제안/`), 적용은 항상 사람 승인 후입니다 — 이 문서·SKILL.md 변경은 자동으로 일어나지 않습니다.
- **`CLAUDE_CODE_SUBAGENT_MODEL` 환경변수는 설정 금지.** 설정 시 Workflow(Ultracode) 내 per-stage 모델 라우팅(위 3단 릴레이 티어맵 포함)을 조용히 전부 덮어씁니다(공식 문서 확인).
- **실행 모드 중에도 판단력이 중요한 순간엔 `advisor()`를 능동적으로 호출하세요.** 훅 시스템엔 이 턴의 응답 모델을 강제로 바꾸는 기능이 없어(공식 확인), 메인 대화 모델은 플랜모드 토글(사용자가 직접)로만 바뀝니다 — 토글을 기다리지 말고, advisor()(항상 `advisorModel: fable` 고정 호출)를 적극 활용하는 게 실행 모드 중에도 상위 모델의 검토를 받는 실질적 방법입니다.

## 계획 우선 (ultraplan)

- 비자명한 작업은 코드를 건드리기 전에 먼저 계획을 세워 제시하고, 단계로 나눠 진행하세요.

## 작업 플레이북 (작업유형 카탈로그)

- 공통 작업유형(요구사항 확정·리서치·의사결정·검토)은 `claude-config/claude/playbooks/`(레포 경로는 `~/.claude/.config-sync-path`)의 플레이북을 참조해 *일하는 법*을 일관되게 적용하세요(도메인 무관·콜드스타트 시드). 비자명 작업이면 해당 플레이북의 **품질 바**를 완료 기준으로 삼습니다. 발견·적용·증식 절차는 `claude/skills/playbooks/SKILL.md`.
- 반복되는 잘 통하는 방법을 발견하면 `/retro`→`/promote`(사람 검토)로 플레이북에 증식하세요. **단 PII·실명·고객정보는 PUBLIC에 절대 올리지 않습니다**(일반화한 방법만).

## 도구 선택 단계 (실행 전)

- **기본 자세 = 최대한 적극(공격적)**: 설치된 도구는 **알아서 적극 활용**(작업에 맞는 전문 플러그인/스킬/에이전트가 있으면 기본으로 사용), 비자명 작업은 **요구사항을 먼저 확정**한 뒤 실행. **어지간한 작업이면 도구·딥인터뷰를 기본 적용**하고, 망설여지면 적극 쪽을 택하세요. **오직 진짜 사소·자명한 것(단순 사실 답변·한 줄 단답·자명한 1줄 수정)만** 생략(lightest-weight) — 그 외에는 적극.
- **사소하다고 판단해 도구를 생략할 땐 투명성 노트를 남긴다**: 매번 물어보고 확인받는 마찰 대신, 애매한 경계선(비자명일 수도 있는데 사소 쪽으로 판단한 경우)에서만 응답 끝에 "이건 사소하다고 판단해 도구 없이 바로 처리함" 류의 한 줄을 남기세요 — 사용자가 그 자리에서 즉시 교정할 수 있게. **극단적으로 자명한 것(인사·단순 사실 확인 등)엔 노트도 생략** — 노트 자체가 소음이 되면 안 됨. 판단이 틀렸다고 사용자가 지적하면 즉시 그 유형을 다음부터는 도구 경유로 상향.
- **작업이 커질수록 도구 경유를 강화하지, 건너뛰지 않는다**: 실측 세션 감사(2026-07-13, 로컬 세션 수백 건 분석)에서 액션 수(Bash/Edit/Write) 6회 이상인 "실질 작업" 세션 대부분은 확장도구(Skill/Agent/MCP)를 잘 활용했지만, **가장 크고 복잡한 세션(89~132회 액션 — 근본원인 디버깅·신규 기능 빌드)일수록 오히려 확장도구 사용률이 0%로 떨어지는 역설이 확인됨** — "일이 커지니 그냥 혼자 다 처리"하는 경향. 정책 취지와 정반대다. **커밋/프로덕션 코드 변경·신규 기능 빌드·근본원인 디버깅은 규모가 클수록 마무리 전 반드시 `code-review`(또는 해당 도메인 전문 에이전트)를 경유**한다 — "직접 처리가 더 빠르다"는 이유만으로 라우팅을 생략하지 말 것.
- **"Claude 혼자 할 수 있다"는 도구 생략의 근거가 아니다**: 모델 성능만으론 충분치 않다고 보고, 사용자가 만들어둔 신뢰도 있는 전문 스킬·에이전트(도메인 전용 디버거·QA 에이전트 등)를 경유하는 것 자체를 추가 가치로 본다. 망설여지면 무조건 도구 경유.
- 비자명 작업은 deep-interview 취지로 요구사항을 확정한 뒤, **실행 전에** 설치된 플러그인·스킬·에이전트 중 그 작업에 가장 맞는 도구를 먼저 식별·명시하고 진행하세요. (단순/사소한 작업은 이 단계 생략)
- 라우팅 힌트(설치된 base): 브라우저 자동화·스크린샷 → **playwright**, 최신 라이브러리 문서 → **context7**, GitHub 이슈/PR/리포 → **github**(gh 로그인 시 토큰 자동), 차단된 공개 페이지·플랫폼(X·레딧·유튜브·네이버 등) 우회 수집 → **insane-search**(WebFetch 403/차단 시), 보안·시크릿 점검 → **security-guidance**, 결정적 가드레일 → **hookify**, 스킬 제작·측정 → **skill-creator**, 플러그인/MCP 제작 → **plugin-dev·mcp-server-dev**, 신규 UI 코드 품질 → **frontend-design**, 오케스트레이션·검증·리뷰·딥인터뷰·랄프 → **oh-my-claudecode**, 전문 에이전트팀 설계 → **harness**. (배포 등 특화 플러그인은 base 에서 제외 — 필요할 때만 `claude plugin install` 로 그때그때 설치)
- 필요한 능력이 설치돼 있지 않으면 즉석에서 쓰려 하지 말고(플러그인·MCP·훅은 활성화 + 세션 재시작 후에야 동작), 먼저 "설치 + 재시작" 을 권고하세요.
- 대부분의 작업은 이미 깔린 base 로 커버되므로, 매번 새 플러그인을 깔기보다 **가진 것 안에서 라우팅**하는 것을 우선하세요.
- 사용자가 도구 이름을 몰라도, 요청을 받으면 **위 맵으로 가장 맞는 설치된 도구를 알아서 선택·사용**하세요. "어떤 도구 쓸까요?"를 매번 사용자에게 떠넘기지 말 것 — 명백하면 "이 작업은 X(설치됨)로 진행합니다" 한 줄 알리고 바로 진행.

## 플러그인 제안 (미설치 · 검증 게이트) — 좋은 게 있으면 추천하되, 검증된 것만

- base 로 **충분히 안 되는** 작업에서 더 적합한 플러그인이 있으면 **루틴으로 제안**하세요(사용자가 매번 플러그인을 직접 찾지 않아도 되도록). 단 설치는 활성화+세션 재시작이 필요하니 **동의 후**.
- **검증 게이트(필수) — 통과한 것만 추천**:
  - ✅ **공식**: `claude-plugins-official`(Anthropic 큐레이션 마켓) 플러그인은 신뢰 가능.
  - ✅ **검증된 3rd-party**: 활발한 유지보수(최근 커밋·이슈 대응) + 의미있는 채택(GitHub ⭐·실사용자) + 명확한 문서/마켓 등록 — 이 셋이 확인될 때만.
  - ❌ **금지**: 막 올라온·단일 작성자·⭐ 거의 없음·검증/리뷰 없음·관리 끊김. **"딱 하나 있는데 검증 안 된 것"을 괜찮다고 판단하지 말 것.**
  - **불확실하면 추천하지 않는다**(보수적 기본값). 추측으로 신뢰도를 단정 금지. 보안 민감(시크릿 접근·코드 실행)일수록 기준을 더 엄격히.
- **검증 방법**: 3rd-party 추천 전 가능하면 **github MCP**(repo stars·최근 커밋·이슈/PR 활동)로 신뢰 신호를 실제 확인하고 **근거를 함께** 제시. star 수는 단독 신뢰 금지 — 2026년 AI 레포 카테고리는 star 조작이 실측 확인됨(CMU/ICSE 2026, 유기적 fork/star 비율 대략 0.10~0.24대). fork·watcher·issue 활동 비율이 유사 규모 정상 레포의 1/10 이하이거나 생성일 대비 star 급증이면 위험신호로 보고, 최근 활동은 `list_commits`(커밋 로그) 실측으로 확인하세요 — `updated_at` 필드 단독 신뢰 금지. 확인 불가하거나 신호가 약하면 추천 보류.
- **발견(능동 탐색) — "없으면 찾는다"**: base 로 안 되는 작업이면 "후보가 없다"로 끝내지 말고 **github MCP 로 인기순(stars·최근 활동) 후보를 먼저 탐색**(예: `search_repositories sort=stars`)한 뒤 검증 게이트를 적용해 좁히세요.
- **중복·효율 분석 → 교체까지**: 찾은 후보를 **기존 base 와 비교 분석** — ① **중복**(같은 능력)이면 추천 안 함(base 유지), ② base 에 **없는 갭**을 메우면 추가 제안, ③ 기존 것보다 **명백히 더 효율·적합**하면 **교체(replace) 제안**도 가능. 교체는 영향이 크니 **근거(무엇이 왜 더 나은지)·마이그레이션 비용·리스크·충돌**을 함께 제시 + 검증 게이트를 더 엄격히 + **반드시 동의 후**. (인기 높아도 base 와 충돌하면 reject — 인기≠추천.)
- **제안 형식(한 작업당 1회)**: "이 작업엔 `<플러그인>`이 잘 맞습니다 — <왜 적합>. 신뢰근거: <공식 / ⭐N · 최근 활발 / 유지보수>. 설치할까요? (활성화 후 새 세션 필요)" 거절하면 같은 작업에서 다시 권하지 않음. **교체 제안 시**: "`<기존>` → `<새것>` 교체 권장 — <더 나은 점>. 비용·리스크: <마이그레이션·충돌>. 신뢰근거: <⭐N·활발>. 바꿀까요?"
- 우선순위: **설치된 base 라우팅 > 검증된 미설치 플러그인 제안 > (검증 안 되면) 제안 안 함**.

## 딥인터뷰 · OMC 모드 (적극 — 단 슬래시 명령·설치는 제안)

  - **올리는 PR마다 자동 코드 리뷰**(항상 켜둠)를 원하면 → 그 레포에서 **`claude-review`** 한 번 실행 권고(GitHub Action + 구독 OAuth 토큰 방식, 슬래시 아님; 자세히는 README §7). 인증은 `claude_code_oauth_token` 입력, **토큰은 레포에 저장 금지**.

## 공통 지침 착지점 (Vault 10_컨텍스트 = 정본)

- 사용자가 지속 적용될 지침·규칙·선호를 주면 옵시디언 Vault `10_컨텍스트`에 기록하세요 — Claude Code·hermes-agent 등 모든 AI 시스템의 공통 착지점(single source of truth)입니다. 쓰기 방법은 `claude-config/claude/protocols/vault-write.md` 참조(승인게이트 없음, 직접 Write/Edit 또는 `vault-obsidian` MCP).
- **실시간 패턴 기록(주간 배치를 기다리지 않음)**: 대화 중 사용자의 선호·강점·약점·반복되는 판단 패턴이 관찰되면, 주 1회 학습파이프라인을 기다리지 말고 그 자리에서 바로 `10_컨텍스트`(강점_약점_보완.md/업무_원칙_방법론.md/AI_협업_패턴.md 등 해당 캐노니컬 문서)에 반영하세요. 추가 LLM 호출이 아니라 지금 턴 안에서 처리 — 비용 증가 없음. 매 턴마다 별도 분석을 도는 건 하지 않습니다(비용·응답지연 커짐, 2026-08-19 판단).
- **단, Vault 기록을 넘어 claude-config 자체(이 CLAUDE.md·스킬·훅·설정)의 동작·권한·모델링을 바꾸는 규칙**이면 즉시반영하지 말고 `retro`→`promote`와 동일한 드래프트+사람승인 절차를 거치세요(순수 관찰/기록성 규칙만 즉시반영 대상). 정밀한 승인조건은 아직 설계하지 않았습니다 — 데이터가 더 쌓이면 그때 사람과 함께 판단합니다. (2026-08-19, 딥인터뷰로 확정)
- Claude Code 자체 auto-memory(이 세션의 `~/.claude/projects/.../memory/`)는 캐시/보조로 취급하세요 — 지침 정본을 거기에만 남기지 마세요. 두 곳에 이중 기록해도 무방하되(auto-memory는 이 시스템 고유의 세션 요약·판단력 향상용), Vault 기록이 없으면 hermes-agent 등 다른 시스템이 그 지침을 영영 모릅니다.
- 세션 시작 시 SessionStart 훅(`vault-context.sh`)이 `10_컨텍스트` 요약을 자동 주입합니다 — 그것부터 최신 지침으로 삼으세요.
